# Итерация 1 — SQLite и доменная модель

## Что сделано

- **ADR-0002 подтверждён:** `better-sqlite3@^13` работает в реальном
  Electron-процессе без пересборки (N-API prebuild) — см. обновлённый
  `docs/decisions/0002-sqlite-driver.md` и раздел "Проверки" ниже.
- Миграции: `src/main/db/migrate.ts` + `migrations/0001-initial-schema.ts`
  — таблицы `projects`, `activity_events`, `work_sessions`,
  `session_edits`, `worklog_drafts`, `settings`, журнал `_migrations`.
  Каждая миграция — отдельная транзакция; повторный запуск — no-op.
  (`issues_cache`/`jira_submissions` отложены до Итерации 7 — ADR-0004.)
- `createDatabase()` включает WAL и foreign keys; `app-database.ts` —
  синглтон на реальном `app.getPath('userData')`, вшит в старт/остановку
  приложения (`src/main/index.ts`), плюс автоочистка `session_edits` старше
  30 дней при каждом открытии (FR-04.8).
- Репозитории: `ProjectsRepository`, `ActivityEventsRepository` (insert-only
  + `listByRange`), `WorkSessionsRepository` (CRUD + атомарные
  `update`/`softDelete`/`restore`/`undoLastEdit`, каждая мутация пишет
  snapshot до/после в `session_edits` в одной транзакции),
  `SessionEditsRepository` (insert-only журнал + `pruneOlderThan`),
  `WorklogDraftsRepository`, `SettingsRepository`.
- Валидация инварианта `endedAtUtc > startedAtUtc` — и на уровне приложения
  (`InvalidSessionIntervalError`), и на уровне самого SQLite (`CHECK`
  constraint — защита, даже если кто-то напишет в таблицу напрямую, минуя
  репозиторий).
- Доменные типы в `src/shared/types/`: `project.ts`, `activity-event.ts`,
  `work-session.ts`, `session-edit.ts`, `worklog-draft.ts`.
- Тестовая фикстура дня (`tests/fixtures/sample-day.ts`) — воспроизводит
  E2E-сценарий №1 из ТЗ (09:00–10:30 OB-448, idle 10:30–11:00, 11:00–12:00
  OB-419); переиспользуется и будет переиспользована Session Engine
  тестами в Итерации 4.
- 39 тестов в 8 файлах (`tests/integration/*.test.ts`) — миграции,
  персистентность после "перезапуска", CRUD каждого репозитория,
  конфликт интервалов, journal/undo, параллельные правки, retention.

### Критическая проверка ADR-0002 (better-sqlite3 внутри Electron, не просто Node)

Отдельный smoke-test (`electron-sqlite-smoke.cjs`, временный файл, удалён
после проверки): запуск `better-sqlite3` внутри настоящего Electron
main-процесса — создание in-memory БД, запись, чтение:

```
SMOKE_OK {"id":1,"v":"hello-from-electron-main"} electron=44.5.1 node=24.21.0 NODE_MODULE_VERSION=149
```

Сработало без единого шага пересборки (`@electron/rebuild` не понадобился)
— пакет распространяется как N-API prebuild-бинарник на платформу/архитектуру,
не привязанный к конкретной версии Node/V8.

### Сквозная проверка реального приложения (не только тестов)

`npm run dev`: приложение стартует без ошибок, открывает БД при
`app.whenReady()` **до** создания окон. Подтверждено, что реальный файл
создаётся по реальному `userData`-пути:

```
%APPDATA%\devlog\devlog.sqlite3       4096 bytes
%APPDATA%\devlog\devlog.sqlite3-wal     32 bytes
%APPDATA%\devlog\devlog.sqlite3-shm  32768 bytes
```

(WAL/SHM-файлы — ожидаемый побочный эффект `journal_mode = WAL`, не ошибка.)

## Найденная и исправленная ошибка (до коммита)

При первой реализации `WorkSessionsRepository.undoLastEdit()` в SQL-запросе
восстановления состояния **отсутствовал `WHERE id = @id`** — запрос обновил
бы **все** строки `work_sessions`, а не только целевую сессию. Поймано
до коммита при повторном вычитывании кода, закреплено регрессионным тестом
`'undo трогает только свою сессию, а не все строки таблицы'` (создаёт две
сессии, откатывает правку у одной, проверяет, что вторая не задета).
Отмечаю явно, т.к. это ровно тот класс ошибки, который приводит к
катастрофической порче данных ("рабочее суммарное время не должно
незаметно удваиваться/портиться", НФТ раздел 7) — без теста именно на этот
случай баг мог остаться незамеченным, раз все остальные тесты (где в БД
одна сессия) бы прошли и так.

## Оставшиеся риски / сознательно отложено

1. **Обнаружение перекрытия интервалов и конфликт-резолюшн (FR-04.6)** — не
   реализовано. Пока можно вручную создать две пересекающиеся сессии через
   репозиторий без ошибки — защита появится в Session Engine (Итерация 4).
2. **IPC к этим репозиториям не добавлен.** Dashboard/Timeline/Overlay пока
   не могут вызвать ни один метод отсюда — это Итерации 5/6.
3. **`issues_cache`/`jira_submissions` не существуют** — появятся в
   Итерации 7 вместе с Jira-клиентом (ADR-0004), чтобы схему под них не
   пришлось угадывать заранее.
4. **Нативный `.node`-бинарник better-sqlite3 и упаковка (`electron-builder`
   `asarUnpack`)** — не проверено, т.к. упаковки ещё нет (Итерация 10).
   Явно зафиксировано как остаточный риск в ADR-0002.
5. **`split`/`merge` операций пока нет** в `SessionEditOperation`-реализации
   (тип объявлен, методы — нет) — Итерация 4/5/6.
