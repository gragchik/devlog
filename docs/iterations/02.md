# Итерация 2 (Tauri) — Windows Activity Tracker

## Что сделано

- **ADR-0007 подтверждён:** крейт `windows` (windows-rs) заменяет
  несостоявшийся план на `koffi` (ADR-0003, archived, никогда не
  реализовывался на Electron) — в Rust Win32-вызовы типизированы и не
  нужен отдельный FFI-слой.
- `platform::windows_activity_adapter`: foreground-процесс
  (`GetForegroundWindow`→`GetWindowThreadProcessId`→`OpenProcess`→
  `QueryFullProcessImageNameW`), idle-время (`GetLastInputInfo`+
  `GetTickCount64`), блокировка экрана (`OpenInputDesktop`+имя desktop
  **плюс** проверка foreground-процесса на `LockApp.exe`/`LogonUI.exe` —
  см. находку ниже).
- `tracking::whitelist`: дефолтный список (JetBrains IDE, VS Code,
  терминалы Windows) + пользовательский override через `settings`
  (`activityTracker.whitelist`), с безопасным fallback на дефолт.
- `tracking::engine::decide()` — чистая функция состояния
  TRACKING/IDLE/PAUSED/LOCKED/SUSPENDED/UNKNOWN с явным приоритетом; 10
  unit-тестов покрывают все переходы приоритета, включая "пауза важнее
  блокировки экрана" и "detection failure не маскируется под обычную
  работу".
- `tracking::tracker`: `ActivityTrackerHandle` (pause/resume, управляется
  треем) + `start(app)` — фоновый поток, не зависящий от окон, пишет
  `activity_events` каждые ~5 секунд через уже готовый (Итерация 1) слой
  данных.
- Трей: пункт «Приостановить/Продолжить» стал **настоящим** (была
  заглушка в Итерации 0) — переключает `ActivityTrackerHandle`, трекер
  реально пишет `PAUSED` вместо `TRACKING`, пока нажато.

### Критическая находка на реальной машине (не воспроизводимо unit-тестом)

Первая версия `is_session_locked()` проверяла только
`OpenInputDesktop`/`GetUserObjectInformationW` — классическая техника,
которая оказалась **недостаточной**: ручной smoke-тест на реально
заблокированной Windows-сессии показал `foreground=LockApp.exe` (т.е.
экран блокировки реально показан), но `is_session_locked() == false`.
Причина — с Windows 8.1+ экран блокировки рендерится как UWP-приложение
поверх обычного "Default" desktop; настоящее переключение на secure
desktop происходит только при начале ввода пароля. Исправлено: функция
теперь дополнительно проверяет, не является ли foreground-процесс сам
`LockApp.exe`/`LogonUI.exe`. Повторная проверка на разблокированной сессии
дала верный `false`. Подробности — ADR-0007.

Это именно тот класс ошибок, который невозможно поймать unit-тестом
(логика "приоритет Locked > Idle" уже была протестирована и верна — сломан
был **сбор сигнала**, не принятие решения по нему) — только ручная
проверка на реальной машине в реальном заблокированном состоянии.

Подтверждено живыми данными:
- события реально пишутся каждые 5 секунд;
- переключение foreground-приложения (WebStorm ↔ другое) отражается
  немедленно;
- idle-секунды растут с реальным отсутствием ввода и сбрасываются в 0 при

  бездействия не засчитываются" (сама граница в 180с — чистая арифметика,
  уже unit-тестируется; здесь подтверждён реальный источник данных для неё);
- для не-whitelisted процесса реальное имя не попадает в БД
  (`process=excluded`), только категория — FR-02.3/FR-02.4 соблюдены на
  практике, не только в типах.

- [x] Сохраняется только разрешённая метаинформация — не-whitelisted имя

- [~] **Restart** (перезапуск Windows) не образует искусственных часов —
  логически обеспечивается тем же механизмом, что и sleep (разрыв между
  poll → `Suspended`), но не проверено отдельным ручным тестом с реальной
  перезагрузкой машины в рамках этой итерации — чек-лист ниже.

## Чек-лист для ручной проверки

1. Запустить `npm run dev`, поработать в WebStorm и в терминале поочерёдно
   несколько минут — открыть БД (`%APPDATA%\dev.devlog.app\devlog.sqlite3`)
   любым sqlite-просмотрщиком и убедиться, что `activity_events` отражают
   переключения с правильными `appCategory`.
2. Не трогать мышь/клавиатуру 3+ минуты — убедиться, что появляются события
   `state=IDLE`.
3. Заблокировать Windows (`Win+L`), подождать, разблокировать — убедиться,
   что в период блокировки писались `state=LOCKED`, а не `TRACKING`.
4. Усыпить ноутбук (сон), подождать минуту, разбудить — убедиться, что
   после пробуждения появилось одно событие `state=SUSPENDED` с большим
   `idleSeconds`/в `reason`, а не серия `TRACKING` за время сна.
5. В трее нажать «Приостановить» — убедиться, что новые события идут с
   `state=PAUSED`; нажать «Продолжить» — события возвращаются к обычной
   логике.
6. Перезапустить компьютер целиком, запустить приложение заново — убедиться,
   что после перезапуска не появилось гигантского интервала "с вечера до
   утра", засчитанного как `TRACKING` (ожидаемо: трекер просто начинает
   писать новые события с текущего момента, старые остаются как есть).

## Оставшиеся риски / сознательно отложено

1. **Suspend/resume — косвенное определение** (разрыв между poll), не
   нативный `PowerRegisterSuspendResumeNotification`. Риск ложного
   срабатывания при аномально высокой нагрузке CPU, задерживающей
   poll-поток без реального сна — не проверено отдельно. См. ADR-0007.
2. **Whitelist не редактируется через UI** — только программно через
   `settings` напрямую. UI — Итерация 5.
3. **Git context (branch/issueKey) всё ещё `None`** в каждом
   `activity_event`, как и в Итерации 1 — Итерация 3 подключит это.
4. **Fast User Switching не проверено** — `is_session_locked` может вести
   себя иначе при переключении между несколькими пользователями Windows.
5. **CPU-нагрузка трекера в простое не измерена инструментально** (НФТ:
   цель <2%) — субъективно пренебрежимо мало (один лёгкий poll раз в 5с),
   но не профилировано формально.
