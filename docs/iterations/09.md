# Итерация 9 (Tauri) — надёжность, безопасность, диагностика

## Что сделано

### Crash recovery

- **Отравленный мьютекс БД больше не выключает приложение.** Раньше паника
  в любой команде, захватившей БД, навсегда ломала трекер (`expect`) и все
  24 места захвата (`"database lock poisoned"`) до перезапуска. Теперь
  `AppDatabase::lock()` восстанавливает соединение и снимает флаг
  отравления. Это безопасно: незавершённая rusqlite-транзакция при панике
  откатывается в `Drop`.
- **Паника в одном опросе трекера не останавливает учёт.** Опрос обёрнут
  в `catch_unwind`, паника пишется в лог (panic hook), следующий опрос
  идёт как обычно.
- **Пересборка предыдущего дня** при старте и при смене суток. Раньше
  пересобиралось только "сегодня": последние ~30 секунд дня и работа
  перед падением процесса могли не попасть в сессии вчерашнего дня.
- **Риск №1 из Итерации 4 закрыт:** сессии, на которые ссылается
  черновик worklog, не пересоздаются при пересборке (их id стабильны);
  продолжившаяся работа попадает в новую соседнюю сессию без двойного
  учёта.
- Прерванные падением отправки в Jira → `unknown` (с Итерации 7), теперь
  ещё и считаются и показываются в диагностике.

### Целостность и резервные копии — `db/maintenance.rs`

- При старте: **копия БД перед новыми миграциями** (`VACUUM INTO`,
  хранится 3 последних в `backups/`) → открытие → `PRAGMA quick_check`;
  если проверка не пройдена — байт-в-байт копия файла (и WAL) рядом,
  работа продолжается, ошибка в логе и на экране диагностики.
- Проверки инвариантов, которые SQLite не видит: пересечения
  учитываемых сессий (FR-04.6, двойной учёт), сессии > 12 ч ("гигантский
  интервал"), активное время больше длительности, незакрытые сессии,
  черновики со ссылками на исчезнувшие сессии, отправки `unknown`.

### Экспорт и удаление (раздел 5, FR-02.7) — `commands/data.rs`

- Экспорт **JSON** (все таблицы), **CSV** сессий (с BOM для Excel и
  защитой от CSV-injection), **резервная копия** SQLite. Куда сохранять,
  пользователь выбирает в системном диалоге, который открывает Rust
  (ADR-0009): frontend не может передать путь для записи.
- Удаление: история раньше даты / вся история / всё (+ настройки,
  репозитории и токен Jira). Подтверждение словом «УДАЛИТЬ» проверяется
  **и в Rust**. После удаления — `VACUUM` + обрезка WAL: удалённый текст
  физически исчезает из файлов БД (тест ищет маркер в байтах файлов).

### Безопасное логирование — `logging.rs`

- Файл `%LOCALAPPDATA%\dev.devlog.app\logs\devlog.log`, ротация на 1 МБ
  (текущий + предыдущий), все `eprintln!` заменены.
- **Каждая строка проходит `redact()`**: Basic/Bearer-заголовки,
  `token=`/`"apiToken":`/`password:`, токены Atlassian `ATATT…`,
  `user:pass@` в URL, e-mail, любые непрозрачные строки длиннее 32
  символов. Тексты ошибок Jira в UI тоже идут через `redact`.
- Panic hook: паника в любом потоке оставляет след в логе.
- В лог не пишутся тексты комментариев worklog — только ключ задачи и итог.

### Jira 401/403/429/5xx

- **Исправлен риск дубля:** ответ 5xx на POST раньше считался "точно не
  принято", и повтор был разрешён. Но 502/504 возвращает шлюз перед
  Jira, когда запись уже могла быть создана. Теперь 5xx на POST →
  `unknown` → reconciliation. 401/403/404/429 → `failed`, повтор разрешён.
- 429: в сообщение добавляется `Retry-After` ("повторить через 30 с").

### Гонки

- Тест одновременной двойной отправки одного черновика (с реальным
  чередованием `await`): ровно один POST.
- Правки из overlay/главного окна и трекер работают через один мьютекс.
  Правка detected-сессии, которую трекер только что пересобрал, получает
  "not found" и обновляет список — данные не портятся.

### Диагностика в UI

Settings → **Данные** (экспорт, копия, удаление) и **Диагностика**
(версия, путь и размер БД, схема, целостность, найденные проблемы,
события старта, хвост лога, "Скопировать диагностику").

### Уже было и проверено

- Отказ доступа к Win32 (процесс с повышенными правами,
  `OpenProcess` → ошибка) → состояние `Unknown`, время не начисляется
  (FR-02.6, тесты `engine` с Итерации 2).
- Офлайн: всё локальное работает без сети; Jira-операции без сети не
  портят черновики (тесты Итерации 7).
- CSP в `tauri.conf.json`, capabilities без лишних прав, Jira-команды
  только для главного окна.

## Чек-лист для ручной проверки

1. Settings → Данные → «Экспорт JSON»: диалог сохранения, файл
   открывается, в нём нет токена Jira.
2. «Сессии в CSV» → открыть в Excel: кириллица читается, колонки на месте.
3. «Резервная копия БД» → файл `.sqlite3` открывается любым SQLite-браузером.
4. Удаление «История раньше <даты>» без слова «УДАЛИТЬ» — кнопка
   неактивна; со словом — старые дни пропали из Timeline, новые на месте.
5. Диагностика → «Показать лог»: e-mail и токены заменены на
   `<email>`/`<redacted>`.
6. Во время работы завершить `devlog.exe` в Диспетчере задач, запустить
   снова: в Timeline нет сессии, растянутой на время, пока приложение
   было закрыто.

## Оставшиеся риски

1. **Suspend/resume — по-прежнему косвенно** (разрыв между опросами), не
   `PowerRegisterSuspendResumeNotification` (риск из Итерации 2). На
   практике разрыв > порога уже закрывает сессию; нативная подписка —
   кандидат на доработку после v1.0.
2. **Повреждённая БД** — сохраняем копию и продолжаем, но автоматического
   восстановления (`.recover`) нет: это ручная операция по копии.
3. **Redaction эвристическая**: ловит известные форматы секретов и любые
   длинные непрозрачные строки, но не "короткий пароль словом" вне
   `password=`. В лог такие данные приложение и не передаёт.
4. **Удаление при работающем трекере**: следующий опрос сразу начнёт
   новую историю — это ожидаемо, но стоит помнить при "удалить всё".
