# ADR-0003: Win32 foreground-detector — koffi (план)

**Статус:** ~~принято как план~~ — superseded, см. баннер выше. Этот план
никогда не был реализован на Electron (переход на Tauri произошёл до
начала Итерации 2).

## Контекст

Electron не предоставляет API для получения foreground-окна/процесса другого
приложения (ТЗ FR-02.2: "не полагаться на несуществующий Electron API
foreground process"). Нужно вызывать `GetForegroundWindow`,
`GetWindowThreadProcessId` и получить имя процесса (`QueryFullProcessImageNameW`
или `OpenProcess`+`GetModuleBaseName`) из user32.dll/kernel32.dll.

Варианты:

1. **Нативный N-API addon на C++** (node-addon-api + node-gyp) — максимальный
   контроль, но требует компилятора (MSVC Build Tools) на машине разработки и
   пересборки под ABI Electron, как у `better-sqlite3`.
2. **FFI-библиотека без компиляции** (`koffi`) — чистый JS/N-API биндинг,
   поставляется с прекомпилированными бинарниками под `win32-x64`, использует
   N-API (ABI-стабильный интерфейс), что по данным проекта не требует
   пересборки под каждую версию Electron. Вызовы `user32.dll!GetForegroundWindow`
   и т.д. описываются декларативно, без написания C++ кода.
3. **Внешний helper-процесс** (отдельный скомпилированный `.exe`, например на
   C#/.NET или Rust), который опрашивается через `child_process` и отдаёт
   JSON. Более изолированно (крах helper'а не валит main-процесс), но
   добавляет накладные расходы на создание процесса при каждом poll (цель —
   раз в ~5 секунд, FR-02.1) и требует отдельного шага сборки/подписания
   второго бинарника.

## Предварительное решение

**koffi** — как основной вариант за счёт отсутствия шага компиляции и
ABI-стабильности. План проверки в Итерации 2:

1. Smoke-test на целевой Windows 11 x64 машине: вызвать
   `GetForegroundWindow` + `GetWindowThreadProcessId` + получить имя процесса
   для реально переключаемых окон (WebStorm ↔ Терминал).
   2. Проверить поведение после `electron-builder`-упаковки (не только
   `npm run dev`), т.к. поведение нативных/FFI-зависимостей внутри asar может
   отличаться — `koffi` обычно требует `asarUnpack` для своего бинарника.
3. Если тест не проходит (блокировка загрузки нативного модуля политикой ОС,
   antivirus, enterprise-ограничения) — запасной вариант: helper-процесс
   (вариант 3), т.к. он не требует загрузки стороннего native-кода в сам
   Electron-процесс.
