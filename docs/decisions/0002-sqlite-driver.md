# ADR-0002: SQLite-драйвер — better-sqlite3

**Статус:** принято и проверено (Итерация 1).

## Контекст

ТЗ требует SQLite с WAL и транзакциями для сессий/черновиков/отправок,
библиотеку — "выбрать с проверкой совместимости с Electron и работой
native-модулей после сборки" (раздел 2).

Варианты:

- **better-sqlite3** — синхронный API, самый быстрый вариант для Node/Electron,
  широко используется в production Electron-приложениях. Нативный модуль
  (node-gyp, с опциональной сборкой под N-API), требует пересборки под ABI
  Electron (`@electron/rebuild` / `electron-builder install-app-deps`) при
  несовпадении версии Node, с которой ставился пакет, и Node, встроенного в
  Electron.
- **node:sqlite** (встроенный в Node ≥22.5, experimental) — не требует
  нативной сборки, но в Electron main-процессе доступность и стабильность
  экспериментального API Node под конкретной версией Electron's Node не
  гарантирована и не задокументирована production-ready; на момент решения
  остаётся экспериментальным флагом в Node.
- **sql.js** (WASM-порт SQLite) — не нужен нативный rebuild, но работает
  полностью в памяти с ручной сериализацией на диск, что плохо сочетается с
  требованием WAL/durable-транзакций при crash (FR, НФТ "atomic writes,
  recovery при crash").

## Решение

**better-sqlite3@^13**. Проверка показала, что начиная с этой линии пакет
распространяется как готовые **N-API prebuild-бинарники на платформу/архитектуру**
(`prebuilds/win32-x64.node` и т.д., `gypfile: false` в `package.json` —
компиляция не запускается вообще), а не как ABI-привязанные к конкретной
версии Node/V8 сборки. Поскольку N-API — стабильный интерфейс между
Node/Electron и нативными модулями, **пересборка под Electron (`@electron/rebuild`
и подобные) не потребовалась**.

## Проверка (выполнена)

Smoke-тест: запуск `better-sqlite3` внутри настоящего Electron main-процесса
(не просто Node) — создание in-memory БД, запись, чтение:

```
SMOKE_OK {"id":1,"v":"hello-from-electron-main"} electron=44.5.1 node=24.21.0 NODE_MODULE_VERSION=149
```

Сработало без единого шага пересборки. Примечание: `process.versions.node`
внутри Electron (`24.21.0`) отличается от Node хост-системы через nvm
(`25.9.0`) — Electron несёт свой встроенный Node, это ожидаемо и есть ещё
один довод в пользу N-API-пакетов (не зависят от версии хост-Node, с которой
выполнялся `npm install`).

**Остаточный риск:** после `electron-builder`-упаковки (Итерация 10) нужно
убедиться, что `prebuilds/win32-x64.node` действительно попадает в
финальный `asar`/`app.asar.unpacked` (нативные `.node`-файлы обычно нужно
явно анпакать через `asarUnpack` в конфиге electron-builder) — отложено
до Итерации 10, помечено как риск там же.
