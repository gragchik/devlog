# ADR-0002: SQLite-драйвер — better-sqlite3

**Статус:** принято как план; практическая проверка совместимости —
Итерация 1 (ещё не выполнена, зависимость пока не добавлена в `package.json`).

## Контекст

ТЗ требует SQLite с WAL и транзакциями для сессий/черновиков/отправок,
библиотеку — "выбрать с проверкой совместимости с Electron и работой
native-модулей после сборки" (раздел 2).

Варианты:

- **better-sqlite3** — синхронный API, самый быстрый вариант для Node/Electron,
  широко используется в production Electron-приложениях. Нативный модуль
  (node-gyp, с опциональной сборкой под N-API), требует пересборки под ABI
  Electron (`@electron/rebuild` / `electron-builder install-app-deps`) при
  несовпадении версии Node, с которой ставился пакет, и Node, встроенного в
  Electron.
- **node:sqlite** (встроенный в Node ≥22.5, experimental) — не требует
  нативной сборки, но в Electron main-процессе доступность и стабильность
  экспериментального API Node под конкретной версией Electron's Node не
  гарантирована и не задокументирована production-ready; на момент решения
  остаётся экспериментальным флагом в Node.
- **sql.js** (WASM-порт SQLite) — не нужен нативный rebuild, но работает
  полностью в памяти с ручной сериализацией на диск, что плохо сочетается с
  требованием WAL/durable-транзакций при crash (FR, НФТ "atomic writes,
  recovery при crash").

## Решение

**better-sqlite3**, с обязательной пересборкой под ABI Electron через
`@electron/rebuild` как postinstall-шаг, и smoke-тестом (создание файла БД,
запись, чтение, перезапуск Electron-процесса) до того, как на неё будет
опираться любая бизнес-логика. Если смок-тест провалится на целевой Windows
x64 конфигурации — запасной вариант: `node:sqlite`, если к Итерации 1 он уже
стабилен в используемой версии Electron/Node, иначе — `sql.js` с явным
WAL-журналом, эмулированным через чтение/запись файла на каждый checkpoint.

## Статус проверки

Не выполнено. Это задача Итерации 1 ("Готово, когда: CRUD сессий и миграции
протестированы; перезапуск не теряет записи; две параллельные правки не
повреждают БД").
