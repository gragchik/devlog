# Техническое задание: DevLog — персональный автоматический Worklog для Windows

**Назначение документа:** спецификация для последовательной реализации в Claude Code.
**Целевая платформа:** Windows 11 (x64); Windows 10 — по возможности, без обязательств в MVP.
**Основной пользователь:** один разработчик, локальная установка, без командного режима и облачного backend.
**Статус:** план разработки, не описание существующего приложения.

## 1. Цель и результат

Разработать локальное desktop-приложение, которое без ручного запуска таймеров собирает минимальные сигналы рабочей активности, сопоставляет их с Git/Jira-задачами, формирует историю рабочих сессий и черновики worklog за день. На следующее утро пользователь открывает подготовленный отчёт, при необходимости исправляет время и описание и вручную подтверждает отправку в Jira.

**Обязательная особенность:** быстрое всплывающее overlay-окно поверх WebStorm/других приложений. Overlay должно показывать текущую задачу и историю за сегодня/вчера и позволять редактировать сессии без открытия главного окна.

**Границы автоматизации:** приложение не читает мысли и не может надёжно установить, какая интеллектуальная работа велась только по активному окну. Неопознанное время показывать как «Нераспределено», а не приписывать задаче с выдуманной точностью. В Jira не отправлять данные без явного подтверждения.

## 2. Стек и принципы

- **Tauri 2.x** (Rust backend/core + системный WebView2 на Windows), React, TypeScript, Vite — фронтенд собирается Vite как обычное SPA, Rust-часть (`src-tauri/`) — через Cargo/Tauri CLI.
- SQLite для локальной БД — `rusqlite` (с фичей `bundled`, чтобы не зависеть от системной libsqlite3) в Rust-коде; доступ из frontend только через Tauri-команды, не напрямую. Миграции БД обязательны.
- Vitest для unit/integration фронтенда; `cargo test` для unit/integration Rust-кода (БД, трекер, парсинг); Tauri's WebDriver (`tauri-driver` + WebdriverIO/аналог) или ручной сценарий для e2e UI — выбор зафиксировать в ADR.
- Сборка Windows installer — встроенный Tauri bundler (`tauri build`, NSIS/MSI через `tauri.conf.json#bundle`); отдельный инструмент не нужен (в отличие от Electron Forge/electron-builder).
- Один Rust-процесс (core + все webview-окна в одном процессе у Tauri, в отличие от Electron с его per-renderer процессами), одно главное окно (создаётся при необходимости), отдельное overlay-окно, системный трей (`tauri::tray`).
- Не запускать HTTP-сервер, если он не нужен. Взаимодействие React с privileged-кодом — только через типизированные Tauri-команды (`#[tauri::command]` + `invoke()`), без прямого доступа фронтенда к файловой системе/ОС.
- Не вводить AI, серверную БД, облачную синхронизацию и IDE plugin в базовый MVP.
- Логика трекинга живёт в Rust-ядре и не должна зависеть от жизненного цикла окон/webview.
- Код разделять по модулям (Rust crate-модули на backend, обычная модульная структура на frontend), а не складывать бизнес-логику в React-компоненты или в один `main.rs`.

## 3. Функциональные требования

### FR-01. Работа в фоне

1. Приложение живёт в трее; закрытие главного окна не завершает слежение.
2. Меню трея: «Открыть», «Показать overlay», «Приостановить/Продолжить», «Сегодня», «Выход».
3. Только один экземпляр приложения. Запуск вместе с Windows — опционально и выключен по умолчанию.
4. Явный индикатор статуса: Tracking / Paused / Idle / Unknown; пауза не маскируется под рабочее время.

### FR-02. Пассивный сбор активности

1. Периодически (цель: каждые 5 секунд, конфигурируемо) получать имя активного процесса, системное idle time и текущее время.
2. Для idle/lock/suspend/resume на Windows использовать нативные Win32-вызовы из Rust (крейт `windows` — официальные `windows-rs` биндинги Microsoft): `GetLastInputInfo` (idle time), `WTSRegisterSessionNotification`/`WM_WTSSESSION_CHANGE` или подписку на `SystemEvents`/power-broadcast сообщения для lock/suspend/resume. Для получения foreground-окна другого приложения — `GetForegroundWindow`, `GetWindowThreadProcessId`, `QueryFullProcessImageNameW` (тот же крейт `windows`), без FFI-библиотек вроде koffi — в Rust это обычные typed-биндинги, не требующие отдельного ADR по FFI-стратегии.
3. Список приложений для учёта: WebStorm, VS Code, терминал и вручную выбранные рабочие программы; остальные приложения по умолчанию исключены или попадают в «Нераспределено» без чувствительных данных.
4. Детали окон/URLs, текст файлов, команды терминала, клавиши, clipboard, скриншоты, пароли, токены и содержимое документов НЕ записывать.
5. При idle дольше 180 секунд, блокировке, сне, ручной паузе закрывать рабочую сессию по последнему подтверждённому активному моменту; период бездействия не считать работой. На восстановлении начинать новый интервал.
6. При отсутствии разрешений или ошибке OS-helper записывать безопасный статус `unknown`, не выдумывать активность.
7. Вся телеметрия по умолчанию остаётся локальной. Пользователь может удалить историю и исключить отдельные приложения/проекты.

### FR-03. Git / Jira-сопоставление

1. Пользователь явно добавляет локальные папки репозиториев.
2. Git adapter определяет рабочую ветку командой `git -C <repo> branch --show-current` (или через безопасный Git API), без чтения исходников. Обрабатывать detached HEAD и отсутствие Git.
3. Извлекать issue key с настраиваемым regex (по умолчанию `\b[A-Z][A-Z0-9]+-\d+\b`, регистр и разделители нормализовать), например `feature/OB-448-mass-payments` → `OB-448`.
4. Правила сопоставления по приоритету: (1) явное закрепление задачи в overlay, (2) активный репозиторий и его ветка, (3) пользовательское правило project → task, (4) «Нераспределено». Предположения помечать confidence и reason.
5. Переключение ветки во время работы завершает старую сессию и начинает новую. Нельзя считать один и тот же временной интервал в двух задачах.
6. GitLab API, коммиты, MR и code review — отдельные opt-in расширения, не обязательны для первоначального трекинга.

### FR-04. Сессии и классификация

1. Группировать смежные наблюдения в сессии по `issueKey`, проекту, активности и idle-паузам.
2. Хранить исходные события отдельно от редактируемых рабочих сессий; ручная правка не уничтожает первичную историю.
3. Сессия имеет `startAt`, `endAt`, фактические секунды, задачу (или null), источник, confidence, описание, статус и признак ручной корректировки.
4. Разделять сессии на границе локальной полуночи, корректно хранить UTC и timezone и показывать локальную дату.
5. Допускать ручные сессии: встречи, изучение документации, обсуждения, архитектурная работа, созвоны и прочее.
6. В случае перекрытия интервалов не допускать автоматического двойного учёта. При ручных правках показывать конфликт и предлагать обрезать/разделить/оставить как неконтролируемое исключение; рабочее суммарное время не должно незаметно удваиваться.
7. Состояния задачи: `detected`, `unassigned`, `reviewed`, `excluded`. Переоценка истории не должна затирать пользовательские правки.
8. Поддерживать undo последней правки и журнал изменений, минимум для последних 30 дней.

### FR-05. Главное окно

1. Dashboard: Tracking status, текущая задача, длительность, итог за сегодня, количество нераспределённого времени.
2. Timeline дня с временными блоками и источником распознавания; переход по датам (сегодня/вчера/календарь).
3. Список задач с суммарным временем, черновиком описания и статусом отправки.
4. Операции: назначить Jira issue, изменить время/границы, разбить, объединить, исключить, восстановить, создать вручную, изменить комментарий.
5. Раздел Worklog Review: составление итогового черновика и отправка в Jira; кнопка «Копировать» для ручного переноса при отсутствии Jira API.
6. Settings: репозитории, включённые приложения, idle threshold, shortcuts, timezone/display, Jira, автозапуск, хранение, приватность.

### FR-06. Overlay (обязательная функция MVP)

**Сценарий:** работая в WebStorm, пользователь нажимает `Ctrl+Alt+W` (настраивается) и получает маленькое окно поверх IDE, без перехода в главное приложение.

1. Реализовать **отдельное** окно (`tauri::WebviewWindowBuilder`, ~480–560 px шириной), frameless (`.decorations(false)`), с закруглённым UI, `.always_on_top(true)`, `.skip_taskbar(true)`; прозрачность окна (`.transparent(true)`) использовать только если она нужна и стабильно работает в Windows.
2. Вызывать через плагин `tauri-plugin-global-shortcut`, tray menu и кнопку главного окна. Учитывать отказ регистрации shortcut (конфликт с другим приложением), показывать предупреждение и разрешать назначить другую комбинацию.
3. Позиционировать у правого верхнего края активного монитора, в границах `window.current_monitor()`/`available_monitors()` (API `tauri::Monitor`, аналог Electron `screen.getDisplayNearestPoint(...).workArea`); учитывать 125–200% DPI, несколько мониторов и перемещение taskbar.
4. Открывать без запуска нового процесса, сохранять последнюю позицию по дисплею. Открытие warm overlay — целевой p95 до 500 мс на обычном ПК, измерить.
5. Скрывать через Escape, повторный shortcut, кнопку X и при потере фокуса (последнее — настройка); редактирование не должно пропадать из-за blur. Никакого постоянного click-through поверх IDE в MVP.
6. Верхняя зона: `Tracking/Paused`, текущая задача, таймер, Pause/Resume, переключение задачи и кнопка «+ Сессия».
7. Вкладки **Сейчас / Сегодня / Вчера**; компактная история с диапазоном времени, Jira key, длительностью и статусом «распознано/вручную/не распределено».
8. Редактирование прямо в overlay: выбрать другую задачу по ключу или из списка; изменить start/end/duration; добавить комментарий; split сессии по времени; merge соседних; исключить; undo.
9. Сохранение изменений напрямую через тот же доменный service/SQLite, что и главное окно. Реактивное обновление обоих окон (subscribe на события через IPC). Без отдельной, несовместимой модели overlay.
10. При переключении **текущей** задачи немедленно завершить прежнюю сессию и начать новую. Для задним числом изменённой сессии не переключать текущую без отдельного действия.
11. Автоматическая отправка из overlay не предусмотрена: доступны «Открыть отчёт», «Копировать черновик», опционально отдельный диалог подтверждения отправки после реализации Jira.

**Пример компактного layout:**

```
┌────────────────────────────────────────────┐
│ DevLog        ● Tracking           ✕      │
│ Сейчас: OB-448  • 01:24:10     [Пауза]    │
│ [Сменить задачу]           [+ Сессия]     │
├────────────────────────────────────────────┤
│ [Сегодня]  [Вчера]  [Нераспределено]      │
│ 09:12–10:35  OB-448    1:23   [Изменить]  │
│ 10:40–11:15  Без задачи 0:35  [Назначить] │
│ 11:20–12:05  OB-419    0:45   [Изменить]  │
├────────────────────────────────────────────┤
│ Итого: 2:43       [Отчёт] [Открыть]       │
└────────────────────────────────────────────┘
```

**Тест-кейсы overlay:** вызов поверх WebStorm на двух дисплеях; редактирование при работающем tracker; Esc без потери сохранённых правок; отключение монитора; DPI 150%; быстрые повторные нажатия; конфликт глобального shortcut; отсутствие проекта; переключение задачи в активной сессии; сохранение после перезапуска; блокировка и разблокировка Windows.

### FR-07. Jira

1. Поддержать `JiraProvider` с реализациями `Cloud` и `DataCenter/Server` через adapter interface. Версию/тип Jira определить в настройке соединения; не предполагать, что это обязательно Jira Cloud или Tempo.
2. Функции: проверить соединение и пользователя, получить данные issue по ключу, отправить worklog, прочитать собственные worklog за период (если permissions позволяют), показать результат.
3. Cloud: `POST /rest/api/3/issue/{issueIdOrKey}/worklog`; comment — Atlassian Document Format, `timeSpentSeconds`, `started`; Data Center: совместимый endpoint v2 с отличающейся моделью comment. Не смешивать форматы.
4. Авторизация: поддерживать разрешённую в организации схему; для личного приложения возможен API token/PAT при наличии разрешения, OAuth рассматривать отдельно. Пароли в plaintext не хранить. Секреты шифровать через крейт `keyring` (обёртка над Windows Credential Manager/DPAPI) или `tauri-plugin-stronghold`; выбор зафиксировать в ADR при реализации Итерации 7.
5. Перед POST всегда preview (issue, календарная дата, время, текст, итог). Пользователь выбирает записи и явно нажимает «Отправить».
6. Сохранить mapping `localDraftId → remoteWorklogId`, timestamp отправки, статус, хэш payload. Для `pending/unknown` после сетевого таймаута не выполнять слепую повторную отправку: сначала reconciliation, так как сервер мог принять POST.
7. Проверять локальные дубликаты и, по возможности, уже имеющиеся записи в Jira перед публикацией. Если Jira недоступна — сохранить черновик и дать retry после проверки.
8. Не менять estimate задачи без явного подтверждения; где API поддерживает `adjustEstimate=leave`, использовать его по умолчанию.
9. После отправки сохранять локальную историю без повторной публикации. Редактирование опубликованной записи — отдельный режим с предупреждением и поддержкой API update, только после первой стабильной версии.
10. Если Jira защищена VPN/SSO, показывать понятную ошибку, не обходить настройки безопасности компании.

### FR-08. Черновик описания

1. MVP без AI: формировать нейтральное описание на основе подтверждённых метаданных (issue summary + тип активности), например «Работа над задачей OB-448: разработка и локальное тестирование».
2. Не утверждать, что исправлен баг, реализована фича или прошли тесты, если нет достаточных данных.
3. Позволять редактировать, использовать шаблоны и копировать готовый текст.
4. Дополнительная версия: краткая сводка по commit/MR с opt-in, фильтрацией секретов и явным разрешением на внешние AI API. По умолчанию никакой передачи исходников/коммитов во внешние сервисы.

## 4. Состояния и алгоритм трекинга

**Состояния движка:** `TRACKING`, `IDLE`, `PAUSED`, `LOCKED`, `SUSPENDED`, `UNKNOWN`.

Алгоритм каждого poll:

1. Получить timestamp, system idle time, состояние блокировки/сна, foreground app.
2. Если paused/locked/suspended/idle threshold — закрыть подтверждённую рабочую сессию на последнем валидном timestamp, новый интервал не начислять.
3. Если приложение исключено — не начислять; можно считать только агрегированное excluded time без имени приложения, если пользователь включил эту опцию.
4. Найти текущий repo по явно настроенным правилам; прочитать branch и получить issue key. Неопознанное время оставить `unassigned`.
5. Если task/context изменился — закрыть текущую сессию и открыть новую.
6. Периодически сохранять контрольную точку и событие. При пропуске нескольких poll из-за нагрузки/сна не заполнять пробел как рабочее время автоматически.
7. Осуществлять разрешённое уплотнение событий для экономии диска. Не обновлять SQLite каждую секунду.

**Правила времени:** секунды — основной формат хранения; интервал `[start, end)`, `end > start`; одно локально учтённое мгновение не может одновременно принадлежать двум автоматически определённым задачам. Время после ручной корректировки отличается от «обнаруженного» и маркируется. Делить на локальные дни корректно через timezone, не предполагать что день всегда 86400 секунд.

## 5. Данные (проект схемы)

- `projects`: id, name, repoPath, enabled, issueRegex, preferences.
- `activity_events`: id, timestampUtc, processNameSanitized, appCategory, projectId?, branch?, detectedIssueKey?, idleSeconds?, state, confidence, reason. Сырые заголовки окон не хранить.
- `work_sessions`: id, startedAtUtc, endedAtUtc, timezoneId, projectId?, issueKey?, activeSeconds, manualSecondsOverride?, description?, source, confidence, reviewStatus, deletedAt?.
- `session_edits`: id, sessionId, editedAt, operation, previousStateJson, nextStateJson; ограничение истории и очистка.
- `issues_cache`: issueKey, title, fetchedAt, sourceProvider.
- `worklog_drafts`: id, localDay, issueKey, timeSpentSeconds, startedAtUtc, comment, selectedSessionIds, status, updatedAt.
- `jira_submissions`: id, localDraftId, issueKey, payloadHash, remoteWorklogId?, state(`pending|posted|unknown|failed`), attemptedAt, resolvedAt?.
- `settings`: key, value; sensitive values хранить отдельно в зашифрованном контейнере.

Добавить версии схемы и миграции; SQLite WAL и транзакции для изменения сессий/отправок. Хранить базу в каталоге, который даёт `tauri::Manager::path().app_data_dir()` (аналог Electron `app.getPath('userData')`); экспорт JSON/CSV по явному запросу пользователя; резервное копирование с предупреждением о чувствительности метаданных. Все изменения из overlay и основного окна выполняются через один сервис (один Rust-процесс, общее состояние за `tauri::State`).

```
  capabilities/{default.json,overlay.json}      # Tauri 2 permission-манифесты окон
  icons/
  src/
    main.rs                                      # тонкая точка входа, вызывает lib::run()

    tracking/{activity_tracker,session_engine,git_adapter}.rs

    integrations/jira/{jira_provider,jira_cloud,jira_datacenter}.rs
    services/{session_service,worklog_service,settings_service}.rs
src/                                               # frontend (Vite)
  app/{App,router}.tsx
  pages/{dashboard,timeline,worklog-review,settings}/
  overlay/{OverlayApp,session-editor,quick-switcher}/
  shared/{components,hooks,styles}/
  shared-contracts/{types,schemas}.ts              # зеркалит Rust DTO, вручную синхронизируется или через ts-rs/specta

  (Rust: #[cfg(test)] рядом с модулями + src-tauri/tests/ для integration)
  (Frontend: tests/unit, tests/e2e, tests/fixtures — Vitest)

```

Команды (Tauri commands) вместо Electron IPC whitelist: `get_today`, `get_sessions(date)`, `update_session`, `split_session`, `merge_sessions`, `set_current_issue`, `create_manual_session`, `pause_tracking`, `resume_tracking`, `get_worklog_drafts`, `submit_selected_worklogs`, `get_settings`, `update_settings`. Аргументы валидировать в Rust-коде команды (serde deserialize + явные проверки), не давать frontend прямой доступ к файловой системе/процессам сверх задекларированных в `capabilities/*.json` разрешений. Из Rust в frontend — события через `app_handle.emit("tracking:changed", payload)`/`"sessions:changed"`/`"worklog:changed"`; подписка на фронтенде через `listen()`, отписка (`unlisten`) при размонтировании компонента/уничтожении окна.

## 7. Нефункциональные требования

- Локальная работа полностью без сети; Jira доступна только при явной синхронизации и отдельных opt-in обновлениях issue title.
- Поведение предсказуемое: не приписывать пользователю нераспознанное время, отображать confidence и способ определения.
- Оптимизация: целевой средний CPU трекера в простое <2% на тестовом Windows ПК; сбор не чаще согласованного интервала; замерить фактическое потребление RAM (у Tauri ожидаемо ниже, чем у Electron — один WebView2-рантайм на процесс, нет бандла Chromium) и зафиксировать в README вместо заведомо нереального лимита.
- Обеспечить atomic writes, recovery при crash, защиту от дублирования, idempotent обработку локальных событий.
- Security: минимальный набор Tauri **capabilities** на каждое окно (`capabilities/*.json` — overlay не получает разрешений, которых не требует; например, доступ к Jira HTTP-клиенту и файловой системе только там, где реально нужен), команды валидируют аргументы и вызывающее окно, CSP в `tauri.conf.json#app.security.csp`, никакого произвольного remote-контента в webview, секреты (Jira-токены) только в Rust-слое (никогда не передаются во frontend), безопасное логирование с redaction.
- Без скриншотов, кейлоггера, записи текста редактора, терминальных команд и содержимого браузера. Статус работы всегда видим в трее, пауза доступна одним действием.
- Никакого отправления Jira worklog без пользовательского подтверждения, никаких скрытых uploads или автообновлений без согласия.
- Использование на корпоративном ПК и интеграция Jira должны соответствовать правилам работодателя.
- Поддерживать дату, timezone, DST, два монитора, DPI scaling, отсутствие VPN, reboot, sleep, приложение в фоне.

## 8. План реализации — итерации для Claude Code

**Правило:** каждая итерация — маленький рабочий коммит с тестами; последующие этапы не начинаются до выполнения acceptance criteria предыдущего. Не писать весь проект одной большой генерацией.

### Итерация 0. Исследование ограничений и каркас
**Задачи:** подготовить Tauri 2 + React + TS + Vite (`src-tauri/` Rust-ядро + `src/` frontend); проверить на Windows 11 запуск tray, два окна (main + overlay), Tauri-команд и global shortcut; зафиксировать ADR (SQLite-driver — `rusqlite`, стратегия Win32 foreground detector — крейт `windows`, Jira provider, capabilities-модель вместо Electron-sandbox). Создать README и команды dev/build/test (`npm run tauri dev`, `cargo test`, `npm run tauri build`).
**Готово, когда:** `npm run tauri dev`, `cargo check`/`cargo clippy`, `cargo test`, `npm run tauri build` работают; overlay открывается над другими окнами и закрывается Escape; capabilities ограничены минимально необходимым на каждое окно.

### Итерация 1. SQLite и доменная модель
**Задачи:** миграции и репозитории; типы events/sessions/drafts; валидация; транзакции; тестовая фикстура дня; один источник данных для main/overlay.
**Готово, когда:** CRUD сессий и миграции протестированы; перезапуск не теряет записи; две параллельные правки не повреждают БД.

### Итерация 2. Windows Activity Tracker
**Задачи:** адаптер Win32 foreground process (крейт `windows`); idle/lock/suspend через `GetLastInputInfo`+session notifications; whitelist приложений; пауза через трей; устойчивый сбор раз в ~5 сек (Rust `tokio`/`std::thread` таймер, не JS-интервал).
**Готово, когда:** переключение WebStorm ↔ рабочий терминал отражается в событиях; 3 минуты бездействия не засчитываются; lock/sleep/restart не образуют искусственные часы; сохраняется только разрешённая метаинформация.

### Итерация 3. Git context и связывание с Jira key
**Задачи:** настроенные repos, текущая ветка, regex issue key, приоритеты explicit/branch/unassigned, смена проекта/ветки.
**Готово, когда:** `feature/OB-448` распознаётся; `main` не приписывается произвольной задаче; смена ветки завершает старую сессию; unassigned выделяется отдельно.

### Итерация 4. Session Engine
**Задачи:** группировка событий, разрезание по idle/полуночи, защита от overlapping, recovery и ручные overrides.
**Готово, когда:** сценарии работа–обед–работа, сон, два проекта, рестарт и работа за полночь корректны; итоги не удваиваются; автообновление не затирает ручные правки.

### Итерация 5. Главное окно + история
**Задачи:** Dashboard, Timeline, День/Вчера, список задач, editing, split/merge, manual entries, undo, отчёт по дням.
**Готово, когда:** все операции с сессиями доступны без работы с БД вручную, корректно отражаются итоги и «Нераспределено».

### Итерация 6. Полноценный Overlay
**Задачи:** отдельный always-on-top window, hotkey, tray toggle, 2+ монитора/DPI, быстрый switch задачи, inline session editor, today/yesterday, split/merge, pause, undo, общий service с главным окном.
**Готово, когда:** можно провести полный сценарий корректировки вчерашних сессий **не открывая главное окно**; исправления сразу видны в основном UI; overlay открывается поверх IDE и не блокирует её после закрытия; тесты из FR-06 пройдены.

### Итерация 7. Jira Integration + review
**Задачи:** Cloud/DC provider, подключение, fetching issues, Secure credential storage, drafts, preview, POST worklog, local+remote duplicate checks, pending reconciliation, retry после явного выбора.
**Готово, когда:** пользователь может проверить и отправить несколько записей; network failure не теряет draft; timeout не вызывает дубли без проверки; есть копирование отчёта как fallback; Jira не модифицирует estimate неожиданно.

### Итерация 8. Генерация описаний и удобство
**Задачи:** нейтральные шаблоны, сохранённые комментарии, ручная корректировка, напоминание в приложении о незаполненных вчерашних сессиях, фильтры; без внешнего AI.
**Готово, когда:** отчёт за вчера можно подготовить за 1–2 минуты, если распознавание отработало корректно; описание не содержит неподтверждённых утверждений.

### Итерация 9. Надёжность, безопасность, диагностика
**Задачи:** crash recovery, безопасное логирование, integrity checks, экспорт/удаление данных, отказ доступа к Win32, Jira 401/403/429/5xx, работа офлайн, массовые операции/гонки, redaction.
**Готово, когда:** после принудительного завершения и запуска история консистентна; секреты не попадают в SQLite plain fields, renderer или логи; пройдены unit/integration/security checks.

### Итерация 10. Packaging, QA и релиз v1.0
**Задачи:** Windows installer, иконка и tray, настройка startup, версия приложения, инструкции подключения Jira, документация privacy, smoke test на чистом ПК с двумя мониторами.
**Готово, когда:** установленная программа работает независимо от `npm run dev`; трей/горячая клавиша/overlay/SQLite/Jira работают и после reboot; есть сценарий миграции существующей БД.

### Итерация 11 (после MVP, опционально). JetBrains IDE plugin / GitLab
**Задачи:** IDE plugin (точное определение проекта/ветки и переключения контекста) или интеграция GitLab commits/MR/review с пользовательским разрешением; стабильный локальный протокол IPC. Не собирать содержимое исходников.
**Готово, когда:** повышается точность attribution; при отсутствии плагина приложение продолжает работать без регрессий.

### Итерация 12 (после MVP, опционально). AI Summary
**Задачи:** генерация комментариев только из разрешённых метаданных, локальная модель или отдельное согласие на внешнюю; редактирование и approval каждого текста.
**Готово, когда:** AI никогда не отправляет сырые файлы/секреты без разрешения и не публикует worklog самостоятельно.

## 9. Ключевые тест-сценарии (E2E)

1. Работа 09:00–10:30 `OB-448`, 10:30–11:00 idle, 11:00–12:00 `OB-419` → 1:30 + 1:00, idle не входит.
2. Переключение ветки `OB-448` → `OB-419` → `main`; для `main` создаётся unassigned, прошлые сессии не меняются.
3. Overlay изменяет вчерашнее событие с `OB-448` на `OB-419`, итог обеих задач пересчитывается, изменение видно в dashboard без reload.
4. Overlay разделяет сессию по времени и объединяет соседние; undo возвращает прежние данные.
5. Таймер не продолжает считать при Windows lock/sleep и после закрытия основного окна; продолжает после выхода из idle.
6. Два монитора, 150% DPI: окно overlay полностью видно, Escape закрывает, hotkey повторно открывает.
7. Jira unavailable / 401 / timeout POST: черновик не потерян; после timeout приложение не публикует дубликат автоматически.
8. Созданный и подтверждённый worklog после restart имеет remote ID и статус posted.
9. Принудительное завершение процесса во время работы → корректное восстановление без гигантского интервала «до утра».
10. Никакие tokens/passwords/clipboard/window titles не появляются в event DB или debug logs.

## 10. Definition of Done (v1.0)

- Отслеживание возможно без start/stop; status и pause доступны в трее.
- Привязка к issue key через Git branch, unassigned не теряется.
- Рабочий день можно отредактировать как в основном окне, так и **полностью через overlay**.
- Worklog за вчера получается из локальных сессий; перед публикацией можно изменить сумму и описание.
- Jira posting безопасен, требует подтверждения, поддерживает reconnect и не допускает «слепых» дублей.
- История сохраняется локально при restart/crash, privacy defaults выполнены.
- Есть installer, README, настройки, тесты, миграции, демонстрационные данные.
